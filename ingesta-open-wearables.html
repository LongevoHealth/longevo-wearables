Longevo · Wearables · Diseño 2026-09-11

Ingesta de Open Wearables hacia la API de dominio

El evento avisa; el dato se busca. Open Wearables publica una notificación sin PHI cuando termina un batch, y wearables-api resuelve el detalle contra la API externa. Fase 1: cambia la fuente, no el dominio.

El evento

Coalescido y sin dato de salud

  • Se emite una vez por corrida, en sync_status_service.emit_event — el único seam por el que pasan los cuatro caminos de ingesta, SDK y providers OAuth incluidos.
  • Lleva los dos identificadores: external_user_id para matchear contra user_wearables, y el UUID interno para armar la URL del pull.
  • Ventana temporal y tipos tocados. Nada más.

La frontera

Lo que Longevo no puede hacer

  • Sin ruta de red a Aurora. No es una convención: no existe el camino.
  • El evento viaja por IAM, no por secreto compartido. Se elimina el webhook público.
  • El WAF sólo deja pasar GET sobre los paths de lectura. El flag read_only en la API key queda para v2.

Lo que no cambia

Fase 1 toca la fuente, no el dominio

  • El store de wearables-v2, el matching, los resúmenes B2B y la gamificación quedan intactos.
  • La convivencia con Spike usa DefaultWearableSourceService, que ya existe y está probado.
  • El snapshot-replace por ventana además replica los borrados de provider sin un tipo de evento aparte.
