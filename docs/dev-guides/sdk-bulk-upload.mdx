## When to use which path

The mobile SDK has two ways to deliver a batch:

| Path | Use it for | Feedback |
|---|---|---|
| `POST /api/v1/sdk/users/{user_id}/sync` | Incremental syncs under ~1 MB | Synchronous `400`/`403` on a bad request, `202` once queued |
| `POST /api/v1/sdk/users/{user_id}/sync/s3` | Historical backfill and any batch above the threshold | Synchronous `403`/`422` on a bad request, `200` with the upload form; the batch itself is validated asynchronously, after the upload |

Large batches take the S3 path so a multi-megabyte payload never travels through the
request body or the task broker.

## Flow

1. The SDK calls `POST /api/v1/sdk/users/{user_id}/sync/s3` with its SDK token.
   The response contains `upload_url`, `form_fields`, `file_key`, `expires_in`,
   `max_file_size` and `bucket`.
2. The SDK posts the batch to `upload_url` as `multipart/form-data`: every entry of
   `form_fields` must be sent as its own form field, in the response's order, before
   the file field, and the file field must carry `Content-Type: application/json`.
   Use `file_key` as given — do not construct your own key.
3. The bucket notification reaches `POST /api/v1/sns/notification`, which verifies
   the SNS signature and topic ARN, then dispatches the import to the worker that
   downloads the object and reuses the same import path as the direct-POST endpoint.

The presigned form expires in 15 minutes (900 seconds) by default; you can request
anywhere from 60 to 3600 seconds via `expiration_seconds`. The upload is capped at
200 MB — that ceiling is enforced server-side and cannot be raised. `max_file_size`
only lets you ask for a *smaller* cap (down to 1 KB); a request for more than 200 MB
is rejected with a `422` before any presigned form is issued.

## Object key layout

Keys are `{user_id}/sdk/{batch_id}.json`. The middle segment is what routes the
object to the SDK import rather than the Apple Health XML import, and the first
segment is how the notification handler recovers the user. `batch_id` is generated
server-side as part of the presigned response — do not flatten the key or invent
your own `batch_id`.

## Retries

SNS delivers at least once, and a worker killed mid-task can also cause the same
batch to be redelivered — so a batch genuinely can be processed twice. Whether a
retry is safe depends on what the batch contains:

- **Time-series samples are safe to retry.** This covers both the top-level
  `records` array and the per-metric statistics extracted from each `workouts`
  entry. Every sample is written with an upsert keyed on
  `(data_source, series type, timestamp)` — re-sending the same batch overwrites
  the same rows with the same values instead of adding new ones.
- **Workouts are safe to retry.** Each workout's header row is written with an
  insert keyed on `(data_source, start time, end time)` that is a no-op on a
  conflict, and its detail row (calories, distance, heart-rate stats, …) is only
  ever written the first time that header is actually inserted — so a duplicate
  workout is silently skipped rather than duplicated.
- **Sleep is not confirmed safe to retry.** Sleep sessions aren't a single
  idempotent database write: they're assembled from a Redis-backed state machine
  that accumulates stage transitions and then merges the finished session with any
  adjacent session already stored for that user. Whether re-running the same batch
  reproduces the same session or extends/duplicates it depends on timing (whether
  the prior run's Redis state had already finalized and cleared) and on whether the
  payload carries per-stage boundaries. This has not been verified safe.

Until sleep retries are verified, do not re-upload a batch that contains sleep data
and that may have already reached the server successfully. If a `/sync/s3` upload
or its bucket-event delivery times out and you can't confirm whether it landed,
treat it as ambiguous rather than assuming it's safe to resend.
